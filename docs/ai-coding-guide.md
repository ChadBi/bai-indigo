# AI coding 上手指南

先读 [两位队员任务单](member-tasks.md)，确认自己的模块。队员 1 完成染艺寻踪，队员 2 完成白乡故事；术语与常见问题由主开发者完成。

## 1. 先把现有工程跑起来

拿到最新的 bai-indigo 工程副本，确认存在 `app/` 和 `app/pnpm-lock.yaml`。每人使用独立副本，避免两人同时改同一个目录。当前旧移交 ZIP 不包含最新正式工程。

本指南对应第三阶段业务代码 `8cb7636` 及本次文档。向主开发者确认交付包名／日期或提交号，并确认包含项目约定、接手文档、架构、任务单、指南、共享类型／组件和模块 README；后续以主开发者的新交付标识为准。

使用 Node.js 24.11 或以上版本、pnpm 11.25.0。先检查：

```sh
node --version
pnpm --version
git status --short
```

版本不符合或 pnpm 找不到时，联系主开发者协助准备环境。Git 报“不是仓库”时，先确认副本是否本来就不带 Git：主开发者确认的无 Git 副本仍可正常开发，跳过分支／提交步骤，按第 7 节交付文件；其他情况先核对副本，不自行初始化替代原历史。不要让 AI 删除锁文件、重建 app 或升级整套依赖来解决环境问题。

在工程根目录的终端执行：

```sh
cd app
pnpm install --frozen-lockfile
pnpm dev
```

按终端显示的地址打开网页。通常为：

- 染艺寻踪：`http://127.0.0.1:5173/#/culture`
- 白乡故事：`http://127.0.0.1:5173/#/stories`

端口被占用时以实际输出为准，不关闭来源不明的进程。dev 终端保持运行，停止时按 Ctrl+C；检查命令放在另一个终端，并同样进入 app。

若当前工具环境提供 bundled runtimes，让 AI 先定位并使用它们；不能把该机器的绝对运行时路径写入项目。

## 2. 给 AI 正确的工作区与任务

让 AI 编程助手打开整个 bai-indigo 根目录，这样它能看到项目约定、共享类型和公共组件。修改权限仍限于自己的模块。

工具应能读取文件、展示改动并运行终端。只能聊天的工具，可用于解释代码或生成逐文件修改建议；把代码落到实际文件后仍要自行运行检查。

第一次先让 AI 阅读和解释项目，不立即大改。确认它能准确回答：自己的入口文件是什么、数据从哪里来、允许改哪些文件、如何判断完成。

## 4. 每次只做一个可检查的小步骤

队员 1 的顺序：分类逻辑 → 列表信息 → 图文详情 → 空状态 → 手机与键盘检查。

队员 2 的顺序：列表信息 → 图文详情 → 图片说明与失败反馈 → 模板事件 → 手机与键盘检查。

AI 理解正确后，选择一个小步骤让它实现。不要只说“全部做完，越好看越好”，也不要一次要求重构整个项目。

队员 1 的实现示例：

```text
现在只完成分类筛选，不改其他模块。
从 entries 的 category 动态提取分类，增加“全部”，使用现有按钮和样式变量。
根据所选分类得到展示列表，保留原详情和来源功能。
筛选逻辑如果需要测试，提取到 culture 目录中的纯函数，并用现有 Vitest 检查。
测试用“测试分类 A/B”的 original 条目，不能添加到正式 content 或产品组件。
不要修改 CultureModule 的 props 接口，不增加依赖。
完成后给出修改文件、检查命令及实际结果。没有真实浏览器检查时明确说明。
```

队员 2 的实现示例：

```text
现在只完善故事详情，不改其他模块。
按 body 展示段落，按 images 展示图片，显示 caption、credit 和内容性质。
复用 ContentImage 的失败反馈及 SourceList，不修改它们的源码。
相关入口只读取 relatedPatternIds，继续发出 selectPattern 事件，不调用 router 或 store。
保持关闭、Escape 和焦点恢复；手机不拉伸图片、不横向溢出。
如公共组件无法满足需求，在 stories 目录组合局部组件，或说明具体缺口交给主开发者。
完成后给出修改文件和真实检查结果。
```

每一步都看实际页面，并让 AI 解释最关键的改动。至少要能说清数据从哪里来、哪个条件决定显示、点击按钮之后发生什么。

## 5. 报错时怎么继续问

先保存完整报错和刚执行的命令，不重复让 AI 猜测。发现它尝试改分配目录之外的文件，先停止修改并检查差异。

修复提示词：

```text
刚才在 app/ 执行 pnpm typecheck 失败。
下面是完整终端输出：
【粘贴实际报错】

请先定位错误原因，区分是本模块引入的问题还是已有公共代码/环境问题。
本模块的问题只在我的分配目录内做最小修复，保持共享接口不变。
公共代码的问题说明文件、原因和建议，交给主开发者，不自行越界修改。
不要用 any、@ts-ignore、关闭 strict、删除测试、删锁文件或升级依赖绕过问题。
修复后重跑相关检查，不能没有运行就写“已通过”。
```

没有终端执行能力的 AI，必须说明未执行命令；你自行运行，再把真实结果反馈给它。

## 6. 怎么做界面检查

先在正常页面检查标题、卡片、详情、来源、关闭和模板入口。再使用浏览器开发工具的设备模拟模式，把视口宽度设为 390px，检查横向溢出、文字、图片和按钮。

用 Tab 切换焦点、Enter 激活按钮、Escape 关闭详情，确认焦点回到触发按钮。真实手机检查与电脑模拟检查分别记录，不能混称。

当前正式数据各只有一条。多分类、空列表、多图、坏图和无关联的情况不能仅凭这一条样例宣布通过。纯逻辑可用本目录 `*.test.ts` 里的测试数据；浏览器场景请主开发者提供临时验收数据或检查方法。

现有 Vitest 使用 node 环境，没有组件挂载测试工具。不要为测试自己新增依赖，也不要把假文化资料或永久测试开关放进业务组件。

检查提示词：

```text
请检查本模块的正常、空内容、无图、多图、图片失败、无关联和 390px 布局。
逐项列出能实际运行的检查，并区分代码检查、纯函数测试和浏览器检查。
缺少场景数据时说明需要主开发者提供什么，不伪造正式文化内容。
请先确认终端的工作目录是 app/，再运行 pnpm typecheck、pnpm test、pnpm build。
只报告真实结果；现有核心测试通过不能当成本模块界面已经验证。
```

## 7. Git 与交付

如果副本保留了本地 Git，开始任务前在工程根目录执行：

```sh
git status --short
```

工作区干净时，队员 1 使用 `member-culture`，队员 2 使用 `member-stories`。

队员 1 在自己副本的工程根目录执行：

```sh
git switch -c member-culture
```

队员 2 在自己副本的工程根目录执行：

```sh
git switch -c member-stories
```

分支已存在时用 `git switch 分支名`，不要重复创建。发现已有他人修改，不覆盖、不丢弃，先联系主开发者。

改完后检查范围：

```sh
git status --short
git diff --stat
git diff -- app/src/modules/culture/
# 队员 2 查看 app/src/modules/stories/
```

不使用 git reset --hard、git clean 或整目录替换清理工作区。不要直接复制另一人的 app/、覆盖 package.json 或锁文件。

如需提交，在根目录只暂存自己的目录。例如队员 1：

```sh
git add app/src/modules/culture/
git diff --cached --stat
git commit -m "feat: improve culture presentation"
```

队员 2 改为 stories 目录和对应提交说明。当前没有远端地址，不自行运行推送或添加远端；把自己的模块文件或本次提交交给主开发者整合。

没有 Git 的副本，至少保留开始时的完整工程备份，并只交付自己的模块目录。需要共享配置修改时先说明需求，交由主开发者处理。

交付前提示词：

```text
请只读审查本次改动，不进行全项目重构。
检查是否越过分配目录、修改依赖/接口、编造文化事实、遗漏来源，
或把未执行的检查写成通过。
列出功能、修改文件、运行命令与实际结果、截图、未完成项和需要主开发者补充的数据。
若工作区原本已有其他人的改动，要明确区分，不修改或提交它们。
最后解释这次改动中最关键的一段逻辑，让我能复述它的作用。
```

交付报告可以用以下格式填写，未执行项目写“未执行”及原因：

```text
模块：
完成的功能：
修改文件：
实际命令与结果：
实际浏览器检查：
桌面/手机/详情截图：
资料来源与图片许可：
缺少的数据或未完成项：
提交号或交付目录：
```

## 8. 遇到这些情况交给主开发者

- 公共组件或类型确实不够用，需要改 shared。
- 必须修改路由、store、引擎、内容数据或依赖才能继续。
- 不确定文化事实、图片出处、许可或传统纹样关联。
- 工程副本缺文件、环境版本不一致、Git 冲突或发现他人改动。
- 当前样例不足以完成某个浏览器验收场景。

先完成仍能独立推进的展示部分，再提交具体问题和证据，不让 AI 越界“顺便修好整个项目”。
